# ОШИБКИ.txt — устранение (фикс-сессия 2026-10-12)

Источник: `ОШИБКИ.txt` в корне. Ядро GCC-проверено регресс-тестом (компиляция
патченого `DBCEnums.h` + прогон граничных случаев `LoadStores`).

## Ошибка 1 (фатальная, блокирующая старт)

```
DB2Stores.cpp:984 in DB2Manager::LoadStores ASSERTION FAILED:
  entry->RangeIndex < MAX_BATTLEGROUND_BRACKETS PvpDifficulty bracket (12) exceeded max allowed value (12)
```

**Причина.** В enum `BattlegroundBracketId` стояло `BG_BRACKET_ID_LAST = 11`, то есть
`MAX_BATTLEGROUND_BRACKETS == 12`, а `PvpDifficulty.db2` билда 26124 штатно содержит
слоты 0..12 (слот 12 — брекет 110 уровня). Сам комментарий в коде требует:
«must be max value in PvPDificulty slot + 1».

**Исправление (ядро, 2 файла).**
1. `core/src/server/game/DataStores/DBCEnums.h` — `BG_BRACKET_ID_LAST = 12`,
   `MAX_BATTLEGROUND_BRACKETS = 13` (явно). Все контейнеры, размер которых задан
   этой константой (`BattlegroundQueue`, `BattlegroundMgr`), масштабируются
   автоматически; геттеры брекетов итерируют хранилище данных и от константы не зависят.
2. `core/src/server/game/DataStores/DB2Stores.cpp` — цикл валидации в
   `LoadStores` больше не обрывает процесс по ASSERT: строка за пределами диапазона
   логируется через `TC_LOG_ERROR` и пропускается (`continue`), debug-ASSERT оставлен
   как сторож. Последствие: старт worldserver устойчив даже к «грязным» dbc.

**Проверка.** Отдельный TU с реальным патченным хедером: `static_assert` на
`MAX_BATTLEGROUND_BRACKETS == 13` + цикл-имитация загрузчика по всем 13 слотам —
компилируется (`g++ -std=c++17 -Wall -Wextra`), прогон `PASS`.

## Ошибка 2 (следствие №1)

`[ВНИМАНИЕ] worldserver не подтвердил готовность` — worldserver падал на ASSERT
во время «Initialize data stores...», поэтому readiness-флаг не выставлялся.
Снимается исправлением №1; отдельных правок не требуется.

## Ошибка 3 (предупреждения окружения, не падение)

`[!] PATH содержит libcrypto-*/libssl-* из FireDaemon OpenSSL 4 и %SystemRoot%`
— посторонние OpenSSL в PATH. Фатальным это становится только при статической
сборке без локальных DLL рядом с exe. Лог же показывает: локальные
`libcrypto-3-x64.dll / libssl-3-x64.dll (3.6.5)` на месте, экспорт
`OPENSSL_Applink` присутствует в обоих exe, `OPENSSL_CONF` подставлен play.bat.
**Решение без смены кода:** не удаляя софт, не добавляйте `FireDaemon OpenSSL\bin`
в PATH (или ставьте его после каталога сервера); `play.bat` уже выставляет
`OPENSSL_CONF` на существующий `tools/openssl.cnf`.
